# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Kibitz (formerly Rapid Coach; the repo, URLs, `rc.` storage keys, the IndexedDB name `rapid-coach`, the Lichess OAuth client id and invite links keep the old name so existing users and links keep working): a free chess coach for chess.com and Lichess games, shared with friends and deployed on GitHub Pages at https://leo17coder.github.io/rapid-coach/ (from `main`, repo root). Static site with **no build step and no runtime dependencies** (a dev-only `package.json` exists just for the end-to-end tests; no linter): `index.html` + `style.css` + `app.js` + `config.js`, interface text in `i18n/<lang>.js`, a `privacy.html` page, third-party code and data vendored in `vendor/`, and offline builders in `tools/` (`build-puzzles.py` for the puzzle subset, `build-openings.js` for opening names). Optional accounts use Supabase; the database schema is `supabase/migrations/*.sql` (run by hand in the Supabase SQL editor; setup steps in `supabase/README.md`).

## Releasing

GitHub Pages lets browsers cache files for about 10 minutes, so a new `index.html` can load with an old `app.js`. `index.html` (and `privacy.html` for the stylesheet) reference `style.css`, `config.js`, `i18n/*.js` and `app.js` with a `?v=<version>` query: **change that version in every release that touches those files.** Vendored files have the version in their name and need no query.

## Run locally

The page must be served over http(s), not opened as `file://`, because Stockfish runs in a Web Worker:

```sh
python3 -m http.server 8000   # then open http://localhost:8000
```

To check a change, load the page (Playwright/Chromium is available in cloud sessions) and use a real chess.com username.

## Tests and the feature checklist (required before every pull request)

`FEATURES.md` lists everything the app does: the definition of "nothing broken". **Before opening any pull request, run `npm install` (once) and `npm test`, and go through the [manual] items of `FEATURES.md` that your change could affect. Every item must still work.** If a change has to alter or remove a feature, ask Leo first and update `FEATURES.md` in the same pull request. Never weaken, skip or delete a test to make it pass; fix the app instead.

- `tests/run.mjs`: ~25 end-to-end tests in headless Chrome (puppeteer-core, no framework), ~1 minute, fully offline. `tests/lib.mjs` serves the repo, intercepts the network and answers chess.com (`api.chess.com/pub`) and Lichess (`lichess.org/api`) from `tests/fixtures/` (real games, anonymised: `test_player`, `li_friend`), and makes Supabase and the explorer behave as offline. Any request to another host fails the run.
- The main flow runs in order in one browser profile (onboarding → analysis → Review → Trainer → Progress → Home → Lessons/Openings → Settings → reload → new games → layouts → switch players); two scenarios run in fresh profiles: **V1 data migration** (seeds `tests/fixtures/v1-storage.json`, the exact storage V1 left; rebuild with `tests/tools/make-v1-snapshot.mjs`) and **accounts off** (serves a `config.js` with an empty key).
- Element selectors live in one `SEL` map at the top of `tests/run.mjs`: **when the UI changes, update `SEL`, not what the tests check.** Tests also rely on the localStorage key contract (`rc.cc:<user>.trainer`, `.base.<tc>`, `.months.<tc>`) and on the read-only test hook below.
- **Test hook:** with `?test=1` in the URL, `app.js` exposes `window.rcTest` (`state()`, `puzzle()`, `game(id)`; defined just before the boot line). Keep it working when refactoring; it reads state, it never changes it.
- `npm test -- --only <text>` runs the matching tests plus the main-flow steps they depend on; `--keep-going` continues after a failure. Failures save `tests/failure-N.png`.

## Decisions to keep

- **Everything runs in the visitor's browser**: engine analysis, puzzles, insights. No server compute and no AI/LLM calls. Insights are fixed, hand-written rules in `insights()` in `app.js`.
- **Public game APIs only**: chess.com (`https://api.chess.com/pub/...`), Lichess (`https://lichess.org/api/...`) and the Lichess opening explorer (`https://explorer.lichess.org`, needs a Lichess OAuth token; see `LiAuth`), fetched **one request at a time** (serially, never `Promise.all`). `api()` retries on network errors and backs off on 429; Lichess calls pass `liOpts()`, which waits a full minute after a 429 as Lichess requires.
- **Must stay free to run**: GitHub Pages plus free tiers only (Supabase free plan for accounts).
- **Accounts are optional**: with an empty `supabaseKey` in `config.js` the app must behave exactly as without accounts. Never upload games (they contain opponents' usernames); only analyses, puzzle progress, baselines and linked accounts sync. Every table needs RLS; the browser only ever holds the publishable key.
- **GDPR** (maintainer is in Denmark): keep `privacy.html` in step with what is stored, keep self-service export and deletion working, no analytics or tracking.
- **GPL-3.0** because Stockfish is shipped. Keep `LICENSE` and `vendor/*-LICENSE.txt`. The app is not affiliated with chess.com or Lichess; keep that statement.
- No CDN dependencies at runtime: vendor any new library into `vendor/` with its licence file. Fonts, icons and pieces are self-hosted too (no Google Fonts), so the site makes no third-party requests beyond the game/account APIs.

## Design system (`style.css`, plan in `docs/DESIGN.md`)

- **Identity:** the club room after the games. Warm charcoal, baize green for the one main action per screen, brass (`--gold`/`--xp`) only for motivation. Literata (`--f-display`) for headings and the coach's sentences, Atkinson Hyperlegible Next (`--f-ui`) for everything else; 14 px minimum for secondary text.
- **Themes:** dark is the default and lives on `:root`; light is under `:root[data-theme="light"]` and again under `@media (prefers-color-scheme: light) :root[data-theme="system"]`. `data-theme` is always set (`dark`/`light`/`system`); `UI.v3` marks the one-time move of the old default `system` to `dark`.
- **Interface text:** `T(key, vars)` and plurals `TP(key, n)` read `window.KZ_I18N[LANG]` (English fallback); static HTML uses `data-i18n`, `data-i18n-html` and `data-i18n-attr="attr:key"`, applied by `applyI18n()`. `LANG` = `UI.lang` or the browser language (en, fr, de, da). Dates through `fmtDay`/`fmtTime`/`fmtWhen` (Today, Yesterday, "Sun 15 Nov"), numbers through `fmtN` (Intl).

- **Tokens.** Colour: `--bg --surface --raised --sunken --text --muted --border(-strong) --primary(-hover/-soft) --on-primary --secondary --success/--warning/--error/--info(-soft) --xp --gold --q-brilliant/best/good/inacc/mistake/blunder`; board `--sq-l --sq-d --hl-* --ar-*` (board themes via `:root[data-board=wood|slate]`); type `--f-display` (Literata) and `--f-ui` (Atkinson Hyperlegible Next) with `--fs-*`; space `--s1…--s8`; radius `--r-sm/md/lg/pill`; elevation `--e1/--e2` (sparingly). All text/background pairs meet WCAG AA in both themes. There are no legacy aliases: inline styles in `app.js` (charts, KM cards, eval graph) use the real tokens.
- **Components:** buttons (`button` secondary, `.pri`, `.ghost`, `.danger`, `.link`, `.icon-btn`, `.lg`; all ≥44px), `.seg` segmented radios, `.panel`, `.card-flat`, `.tag`/`.chip`/`.xp`, `.meter`, `.verdict.v-ok/.v-no/.v-info` (coach feedback), `.kpi`, `.skel` skeleton loaders (no shimmer with reduced motion), `dialog`, `.toast`. Icons: `ic(name, cls)` → `<svg class="ic"><use href="vendor/icons.svg#i-name">`; `vendor/icons.svg` is a Lucide subset (add symbols from lucide-static when needed).
- **Display settings** `UI` = `rc.ui` (this browser only): `theme` system/light/dark, `board` green/wood/slate, `pieces` cburnett/bold, `sound`. `applyUI()` sets `data-theme`/`data-board` on `<html>` (an inline script in `<head>` does it before first paint) and redraws every board (`BOARDS`). Settings dialog `#settings` (`setOpen`). Sounds (`Snd.play("move"|"capture"|"correct"|"wrong"|"goal")`) are synthesised with Web Audio, off by default.
- **Board** (`Board(el, {onMove, sound, label})`): SVG with `<image>` pieces from `vendor/pieces/<set>/`, coordinates on the edge, last-move/selection/check highlights, legal-move dots and capture rings, filled arrows. Input: click-to-move, drag-and-drop with a floating piece (pointer events; `noAnim` after a drop) and keyboard (arrows move a cursor, Enter picks up/drops, Esc cancels; announcements in an `aria-live` span). `set(fen, {last})` slides the moved piece (~180ms, none with reduced motion) and plays move/capture sounds when the position follows from the shown one. `Board.lock` blocks input. `EvalBar(el).set(cp, flip)/hide()` draws the vertical eval bar: Review (`REB`) and the Why panel while stepping (`new Why(el, board, bar)` evaluates each stepped position via `wEval`).

## Architecture (`app.js`)

All code sits in one top-level `{ ... }` block (block-scoped, no modules, no globals leaked). `chess.js` is loaded first as a global `Chess` and is the **old 0.x API** (`game_over()`, `in_checkmate()`, `move({from,to,promotion})`), not the 1.x camelCase API. Code style is dense, one-liner-heavy; match it when editing.

**State and cancellation.** Module-level `let`s: `P` (profile `{source: "cc"|"li", user, tc}`), `ALL` (every stored game), `GAMES` (`ALL` filtered to the current source, user and time control, oldest first), `CUR`/`PLY` (game open in Review). `GEN` is a generation counter bumped by `enter()` on every profile switch; long-running async loops (`sync`, the analysis `queue`) capture `GEN` at start and stop when it changes. Any new async work must follow this pattern, and must not touch `P` after the generation changed (it may be `null` after Switch).

**Storage.**
- IndexedDB `rapid-coach` v2 via `DB`: store `games` (keyPath `id`) and store `pending` (analyses pulled from the account for games not fetched yet on this device; kept in the `PEND` map and attached in `refreshGames()`). Game objects are stored without the cached replay fields `_f` (FENs per ply) and `_m` (chess.js move objects), which `replay(g)` rebuilds lazily.
- `localStorage` through `LS`, every key prefixed `rc.`. `profile`, `lastSrc`, `v2` and the sync keys `sb.out` (outbox), `sb.pull.<uid>` (pull watermarks), `sb.init.<uid>` (first full upload done) are global; per-user keys go through `uk(k)` → `<source>:<user>.<k>`: `months.<tc>` (chess.com archive months already fully fetched), `last.<tc>` (Lichess: newest `createdAt` seen, sent as `since`), `trainer` (puzzle progress `{puzzleId: {seen, ok, fail}}`), `base.<tc>` (baseline stats snapshot). V1 keys had no source prefix; a one-time migration at startup renames them to `cc:` and sets `rc.v2`.

**Game record** (`fromApi` for chess.com, `fromLichess` for Lichess, same shape): `{id:"cc-<uuid>"|"li-<id>", source, user, ts, date, color:"w"|"b", opp, myR, oppR, result:"win"|"draw"|"loss", how, eco, moves:[SAN], clocks:[secs remaining per ply], tc, tclass, rules, link}`. `tc` uses chess.com's format (`"600"`, `"180+2"`) for both sources, and `how` uses chess.com's result codes (`timeout`, `resigned`, `checkmated`...), which `fromLichess` maps to via `LI_HOW`. V1 records have no `source` field; use `srcOf(g)`. After analysis it gains `an: {ev:[cp per position, white's point of view, mate = ±10000], best:[UCI best move per ply], depth}`.

**Pipeline.**
1. `sync()` dispatches on `P.source`. `syncCc()` lists `/games/archives`, always refetches the two most recent months and skips older months marked in `months.<tc>`. `syncLi()` reads one NDJSON stream (`perfType`, `clocks`, `opening`; `max=2000` first, then `since`) and adds games in batches as lines arrive. Both keep only games matching the time control (`matchTc`: `"600"` means exactly 10+0, otherwise `time_class`/`speed`).
2. `queue()` is the single serial analysis queue: for every position of each game it calls `Engine.eval(fen, DEPTH=12)`; `Engine` is one Stockfish worker with its own FIFO of UCI jobs. `Engine.eval(fen, depth, front)` resolves `{cp, best, pv}` (`pv` = principal variation in UCI); `front` puts the job at the head of the queue so on-demand work waits for at most one analysis position. Finished games are written back to IndexedDB, then UI, puzzles and baseline are refreshed.
3. `errorsOf(g)` classifies moves by the drop in the mover's win percentage `wp(cp)`: ≥10 inaccuracy, ≥20 mistake, ≥30 blunder. `serious()` = the player's own mistakes and blunders.
4. Puzzles (`buildPuzzles`) are **derived, not stored**: every serious error from a position with `wp ≥ 30` and a known best move; id `<gameId>:<ply>`. A move is accepted if it equals the engine move or is within 8 win-% points of the position's eval.
5. `stats()` (rating, median time used, serious errors per game over the last 20 analysed, score) feeds the Progress tab; `maybeBaseline()` freezes the first snapshot once 10 games are analysed. A manual reset stores `manual: <ISO time>` in the baseline.

**Sync (`Sync`, optional).** Local first: code that changes synced data calls `Sync.mark(kind, key)` (`an` game id, `pz` `account|puzzleId`, `base` `account|tc`, `la` `account|tc`), which queues it in the outbox; `flush()` uploads in chunks with upserts, reading current values from local storage. `pull()` fetches rows with `updated_at` after the stored watermark and merges: analyses fill games that have none (or go to `pending`), puzzle `seen`/`ok` are OR-ed and `fail` takes the max, baselines prefer the latest manual reset and otherwise the earlier date. The first sign-in on a device pulls, then queues everything local (`markAll`). The account id is `<source>:<username>` (`acct()`), the same prefix as the localStorage keys. supabase-js (`vendor/supabase-2.118.0.js`) is injected only when someone signs in or a session exists; sign-in is email OTP (link with PKCE, or the code typed in) so the `#tab` hash routing is never touched.

**Friends (`Fr`, optional).** Needs an account. `profiles` holds the display name, the `share` switch (GDPR consent; off deletes the person's stats via trigger) and a private invite code; opening `?invite=<code>` and signing in calls `add_friend()`, which makes two people friends at once (no pending state). `Fr.publish()` (debounced via `Fr.soon()`, called after analyses, puzzle answers, baseline changes and pulls) upserts one `leaderboard_stats` row for the current account and time control, computed in the browser by `Fr.row()`; the database refuses it unless sharing is on. Friends' rows are read only through the `friends_leaderboard(tc)` and `my_friends()` functions, which expose the display name and source but never usernames or emails.

**Opening trainer.** `buildTree(col, fam)` merges the first `OP_PLY` (24) plies of the current account's games in one colour + `famOf` family into a `Map` keyed by `posKey(fen)` (first four FEN fields, so transpositions merge). A node has visit count, score, moves played (each with its child key `ck`), engine best-move votes and eval from stored analyses, and my error count; `weak` = often an inaccuracy or worse, or score ≥ 10 points below the opening's. Drill (`OD`, `opStep`/`opMove`, board `OB`): opponent moves are picked by frequency (`opPickOpp`, nudged towards lines with due positions by `opNeed`); my move is right if it equals the pinned move (`OPS[k].pin`), else the engine's best, else is within `OP_TOL` (6) win-% (evals via `opEval`, cached). A miss shows arrows and the eval swing and offers replaying the same line. Progress `OPS` = `uk("openings")` `{posKey: {s, due, ok, miss, pin, at}}` with review intervals `OP_IV`; learned = streak ≥ `OP_LEARNED` (3). `uk("opstart")` holds when each opening (`"w|<family>"`) was first drilled; `opEffect()` compares the score before and after it (Progress insight and Openings view). `uk("opsel")` remembers the chosen opening. **Explorer:** `LiAuth` does Lichess OAuth with PKCE (unregistered public client `rapid-coach`; verifier in sessionStorage; `LiAuth.callback()` runs before `Sync.start()` so Supabase never sees Lichess's `?code=`); the token lives only in `rc.li.token`. `Explorer.moves(fen)` is serialised through one promise chain, cached in `rc.lx` (newest 600), backs off a minute after 429, drops the token on 401, and returns `null` whenever unavailable, so the trainer falls back to my own games. Sync kinds `op` (`account|posKey`, newest `changed_at` wins) and `ops` (`account|w|<family>`, earliest start wins) go to tables `opening_progress` and `opening_practice` (`003_openings.sql`); `Fr.row()` adds `openings_learned`.

**Why panel (`Why`, `TW` for the Trainer, `OW` for the opening drill).** One component explains a move with engine lines, computed only on demand: after a wrong move (`tryMove`, `opMove`), on Show answer, and from the "Why?" button after a correct move. `Why.show({fen, played, best, ok, restore})` evaluates at `WHY_D` (14) via `wEval` (front of the engine queue, cached per position in `WEV`), builds "Your move" (`played` + the reply line) and "Better" (`best` + its line) with `wLine`, which replays every move with chess.js, cuts at the first illegal one and extends lines shorter than 6 plies; 8 plies are shown (`WHY_SHOW`). `wLabel` is rule-based: checkmate or a mate score first, then material change at the line's end (not stopping mid-exchange), naming pieces ("loses a knight for a pawn", "wins the exchange"), then "keeps an extra pawn" (not for a wrong move) or "equal material, better/worse position" (|eval| ≥ 0.6); otherwise no label and the sentence shows the eval swing. Stepping (`Why.step`) locks the board (`Board.lock`) and draws the position with the next move as an arrow; "Back to the position" calls the caller's `restore()`. Callers `clear()` the panel when the puzzle, line or move changes; a token check drops stale results.

**Gamification (`GS`, rule-based).** `GS` = `uk("game")` `{days: {"YYYY-MM-DD" (local): {pz, p1, op, ol, rv, rvl, g, n, e}}, badges: {id: ms}, rec: {bw, ls, bb}, set: {int, hide, at}, rev: {gameId: 1}, at}`. Training calls `gAdd({...})`: first solve of a puzzle (`st.x` stops repeats; `p1` if never failed), an opening position right on review (`opGrade`, only when the streak advances; `ol` when it becomes learned), a game reviewed (8 distinct positions of an analysed game seen in `show()`). XP comes only from training (`GX`), never from results. Everything else is derived from `days`: daily goal (`dayU` units vs `GOAL[int]`; puzzle/position 1, review 3), `gStreak()` (freeze earned every 7 streak days, max `FZ_MAX`, used automatically on a missed day), `gXP()`/`gLevel()` (Pawn→King, then King I, II…), weekly challenge `chOf(week)` with `WK_BONUS`. `gCheck()` awards `BADGES` and personal records (first values silently, then a toast); it runs after training, at account load, after analysis and after a pull. `gToast()` is suppressed when hidden and its animation respects reduced motion. Sync kind `gm` (one row per account in `gamification`, `004_gamification.sql`); `gMerge` takes per-field maxima for days, earliest badge times, best records, newest settings and the union of reviewed games. `Fr.row()` adds `gRow()` (weekly XP for the Monday `xp_week`, streak); `lbPassed()` compares friends ahead of you last time with now (`uk("lbseen")`) for "You passed X this week!". `uk("seen")` (last visit, local only) drives "Since your last visit". Uploads go table by table (`flush`), so one failing table only keeps its own changes queued.

**Home (`#home`, `renderHome`).** Default tab for returning users. `planCards()` ranks 3–5 actions by impact (missed puzzles, due opening positions, latest unreviewed loss, new puzzles, unanalysed games, a weak unpractised opening, with fallbacks), each with its XP. Also: since last visit (W/D/L, worst moment per game, biggest swing on a thumbnail board `HTB` that opens Review), progress vs baseline with arrows, the top insight and practised-opening effect, quick actions, the gamification panel (goal ring, streak, level, weekly challenge, badges grid, records, intensity and hide settings) and, signed in with sharing on, a mini leaderboard. On phones the plan comes first (CSS `order`).

**Start screen.** Feature blocks, trust points, an invite banner (`inviteBanner`, when `?invite=` arrives with no profile yet) and a demo: the hero board `HB` with a static Why panel (`HW.render`, the Nd6+ example) that auto-steps (`demoStart`) unless reduced motion is set or the visitor clicks it.

**App shell.** `<aside class="side" id="hdr">`: on desktop a fixed left sidebar (`--side-w`), with the Kibitz logo, the analysis/sync status pill (`#job`), the main nav of four tabs (Home, Review, Train, Progress; `nav a[data-t]`), and the profile button `#profBtn` (avatar, `#whoName`, `#whoMeta`) that opens `#profMenu` (Switch player `#switchBtn`, Sign in/Account `.acctBtn`, Settings `#setBtn`). Train and Progress show `#tabHead`: the tab title and a segmented `#subnav` of their sections (`SUBS`). At ≤900px the aside becomes a slim sticky top bar (logo, status, labelled profile button) and the nav a fixed bottom tab bar (`--tab-h`); don't give `.side` a `transform`/`filter`/`backdrop-filter`, or the fixed tab bar would attach to it. `show1()` toggles `has-side` (off on the start screen).

**Screens.** Review (`RV`, `renderReview`, `reviewView`): `#review` is the card list (`#rvList`: filter chips `RVF` in `#rvChips`, day groups from `dayGroup`, `gameCard`, `#rvMore`); `#review/<id>` is the game view (`#rvGame`, opened by `openReview(g, ply)`, at `keyPly(g)` by default) with `#rvBack`, the result line, `gameStory` sentence, key moments first (plain words via `evPast`/`evWords`), the graph in a `<details>` and a wrapping move list (`.mp` keeps a move number with its moves). Board column (`.board-col`, sticky on desktop) with eval bar and controls, scoresheet column (`.sheet`) with the eval graph, key-moment cards (`.km`) and a scoresheet move list whose buttons carry `q-blunder/q-mistake/q-inacc/q-best` and a `.qm` mark (??, ?, ?!, or a check when the move was the engine's). Trainer and Openings: a session counter row (`sess()`, `TSS`/`OSS`: solved/attempts, run, best run), a `.coach-card` with the prompt (`.verdict.v-move` "your move" state) and verdict banners (`.verdict` with a leading icon placed in the left gutter by CSS, so verdict text needs no wrapper) plus `.v-actions`. Home: plan cards with an icon, title, reason, XP chip and a specific CTA (`c.i`, `c.cta`), the first card highlighted.

**Weakness profile (`TG`, `tagOne`, `wkProfile`, `lsPriority`).** `TG.run()` (after analysis, at account load, when Lessons opens; GEN-cancelled; non-front engine jobs) tags each serious error in the newest `MT_GAMES` (60) analysed games once, caching `g.mt = {v: MT_V, e: {ply: {t: [tags], ph, et, d}}}` on the game (local only, never synced). For each error it asks Stockfish (depth 12) for my best line from the position (`rF`) and the opponent's best line after my move (`rA`), then fixed rules: mate scores → `mate_missed`/`mate_allowed` (+`backrank` when the mating rook/queen lands on my king's back rank); opponent line wins ≥2 → `hang` (first reply takes an undefended or more valuable piece), else `fork_allowed`/`pin_allowed` (geometry after the reply, `isFork`/`lineTactic`), else `tactic_allowed`; my line wins ≥2 → `fork_missed`/`pin_missed`/`skewer_missed`/`material_missed`/`tactic_missed`; otherwise `positional`. `phaseOf` (non-pawn material and ply) and `endType` (kp/rook/minor/queen/mixed). `wkProfile()` sums `d` (win-% drop) per first tag, phase and ending; `lsPriority()` ranks themes plus habits (errors when winning, fast play with low clock use, weakest opening) by points per game, each with a one-line reason and a target (`motTo(k)`: `MOT[k].to` = a puzzle course id `pz-…`, or `MOT[k].fs` = a First steps lesson for new/beginner levels until it's done; the weakest opening targets its opening course (or the trainer), ending types their endgame course). `lsTarget(to, W)` resolves a course to its next lesson in the chapter from `pzRec`. Rules are unit-testable in Node by extracting the section with `vm`.

**Lessons (`#lessons`).** Content is data: `TRACKS` (Tactics & checkmate patterns, Openings, Endgames; all always shown) > courses (`lv`: levels it suits) > chapters (`test`: placement check) > lessons (`steps`) plus `PAGES[lessonId]` teaching pages (paragraphs and diagram boards with arrows). A step is `{f: FEN, g: "best"|"check"|"mate"|"legal", s: [solution UCI], alt: [also right], x: 1 exact only, n: coach note, ok: note after success}`; "best" without `x` also accepts a move within `OP_TOL` win-% of the solution (via `wEval`). **Validate every new step with Stockfish** (legal FEN, side not to move not in check, solution = engine best or within tolerance, every `alt` safe). Level: `lvlAuto()` from rating (Lichess −250) nudged by accuracy, override in `LSP.lvl.v`. Player `LP` (`openLesson`, `openTest`, `lsStep`, `lsMove`): board `LB`, coach banners, Why panel `LW` with eval bar. Progress `LSP` = `uk("lessons")` `{"l:<id>": {s, d}, "c:<id>": {p, d, t}, lvl: {v}}` with `at`; first completion of a step → `gAdd({ls:1})` (XP `GX.ls`, daily goal unit), a completed chapter → `gAdd({lc:1})`; passing a check marks the chapter's lessons done. Sync kind `ls` (`account|item`) → table `lesson_progress` (`006_lessons.sql`; steps max, done/passed earliest, level newest); `Fr.row()` adds `lessons_completed`. Home's plan gets the top priority lesson (or First steps for new/beginner levels).

**Puzzle courses (stage 2, `PZC`, `pzCourse`).** Tactics track = First steps + 13 puzzle courses (hanging pieces, mate in 1, forks, pins, skewers, back rank, mate in 2, discovered attacks, double check, deflection, smothered, mate in 3, mating patterns), ordered by difficulty. Data: a fixed subset (2,926 puzzles, ~300 KB) of the Lichess puzzle database (CC0) built by `tools/build-puzzles.py` (deterministic; rerun with a new `PUZZLE_STAMP` and change `PZ_DIR` to refresh), vendored as `vendor/lichess-puzzles-<YYYY-MM>/<course>.json` (`{course, bands: [[[id, FEN, "uci moves", rating(, pattern)], ...] per band]}`, licence note `vendor/LICHESS-PUZZLES-LICENSE.txt`) and fetched from this site by `pzLoad` the first time a course opens; never fetched from Lichess. The first move is the opponent's (auto-played), then the solution; any checkmate is also accepted (`pzMove`), opponent replies auto-play. Chapters = rating bands `PZB` (≤1000 … 1600–1800, id `<course>-<1..5>`), each with lessons Warm-up/Practice/Challenge (`PZL`, id `<chapter>-a|b|c`, `PZ_N` 6 puzzles, coach note `c.n[j]`) and a `PZ_T` (4) puzzle placement check from the top of the band (pass with ≤1 miss: chapter done, skill raised to the band top). Adaptive: `pzPick` takes the unseen puzzle closest to skill + lesson offset (a missed one comes back first in Practice/Challenge); `pzRate` updates an Elo-style skill (1 clean, .5 hinted, 0 missed) stored as `LSP["c:pz-<course>"].v` (syncs with `ls`, no new SQL). `pzRec(co, W)`: chapter from the skill band, else rating band (chess.com scale, Lichess −250), one band higher when the theme never appears among mistakes of ≥8 tagged games, then the first unfinished chapter; `pzShift` suggests the next/previous chapter after a lesson when the skill leaves the band. Hints (`pzHint`): piece square, then arrow. `PZS` = `uk("pzs")` `{id: 1 clean | 2 missed/hinted}` is local only. Teaching pages `PAGES["pz-<course>"]` add block types `{h, l}` checklist, `{w, m, t, c, src}` worked example stepped with Next/Back (from real puzzles), and diagram orientation `o`. Validate page positions with chess.js + Stockfish and vendored puzzles with chess.js after any change.

**Opening courses (stage 3, `OPC`, `opCourse`).** Openings track = 12 courses (principles, Italian, London, Scandinavian, Caro-Kann, French, Scotch, Queen's Gambit, QGD & Slav, Ruy Lopez, Sicilian, English & Réti; order set in `TRACKS`). A course has `re` (matches `famOf` names of my games), line chapters `{id, name, side, r: [lo, hi] rating range, lessons}` and a generated "tactics in this opening" chapter (`<id>-t`, puzzles from `op-<id>.json`, all bands as one pool with range `rg`, skill `c:pz-op-<id>`). A lesson is one hand-written line `{id, name, side?, m: "SAN moves", n: {ply: note}, bad: [opponent mistakes in trap lines], end}`, played twice (`steps: [{ln}, {ln, mem: 1}]`: guided with notes, then from memory) by `lnStart/lnNext/lnMove`: the coach plays the other side; my move must be the line move, a move within `OP_TOL` (via `wEval`) is called fine and the line move asked for, anything else shows the Why panel. **Validate every line with Stockfish** (each move within `OP_TOL` of the best at depth 16, `bad` plies really ≥ `OP_TOL`) and keep my moves consistent within a lesson. Placement check per chapter (`opTest`: up to 4 noted key moves of mine from its lines, exact move). `opPlays(co)` counts my games per colour the course teaches; `opRec(co)` = first unfinished line chapter for that colour whose range reaches above my rating (`pzR0`); courses I play (≥3 games) are marked and open. The priority list's weakest opening links to its course (`opCourseFor`). "Drill this line in the opening trainer" (`opDrill`) pins my moves (`OPS[k].pin`) and opens the trainer on a matching family; `opLines(col, fam)` (lines with ≥ 2/3 of my moves pinned) join `buildTree` (nodes get `ln`, count as core positions, weight opponent moves) and add `"<col>|<course name>"` options when I have no games in it. Opening names: `tools/build-openings.js` keeps the lichess-org/chess-openings (CC0) names of positions in the lines, `vendor/chess-openings-2026-11/names.json` (key: first three FEN fields), fetched by `opNames()` and shown under the board. Teaching pages `PAGES["op-<id>"]` may use `{s: "SAN moves", a, c}` diagrams.

**Endgame courses (stage 4, `EGC`, `egCourse`).** Endgames track = 5 courses (basic mates, king and pawn, rook, minor pieces, queen endings & technique) with `et` = the `endType` keys they train. Hand-written chapters `{id, name, r: [lo, hi], lessons}`; each lesson is one pattern with a teaching page `PAGES[<lesson id>]` and steps of two kinds: "find the move" (the normal step format; placement check per chapter = its find steps) and "play it out" `{f, play: "win"|"draw", max, n, ok, d?}` (`egStart/egMove/egFail`): I play against Stockfish at `EG_D[lvl()]` (6–14) or `d`; win = checkmate, or a promotion keeping ≥ +4; draw = a draw by the rules or `max` moves survived; a move that drops a win below +1.5 (a draw below −3), stalemate in a win, or running out of moves fails, with take-back and a hint arrow. **Validate every endgame step with Stockfish** (find: solution within `OP_TOL` of the best, `x` = the best; play: win ≥ +3, draw |eval| ≤ 1). Courses with `pz` also get a puzzle chapter per band `EGB` (≤1000 … 1800–2200, id `<course>-p<1..6>`, `rg` = the band) from `eg-<pz>.json` (Lichess endgame themes, built by `build-puzzles.py`; `pzPool` uses one band, `all` chapters like opening tactics use every band); skill `c:pz-eg-<pz>`. `egRec(co)`: the lesson chapter whose range contains my rating, else the puzzle chapter for my skill/rating band, else the first unfinished one. The priority list's ending items link to `egCourseFor(endType)`.

**UI.** Hash routing (`ROUTES`): `#home`, `#review` (and `#review/<game id>`), `#train/puzzles`, `#train/openings`, `#train/lessons` (`#train` reopens the last section), `#progress`, and `#progress/friends` when accounts are on; each shows one `<section id="v-...">`. `route.cur` is the path (also `rcTest.state().route`), `route.sec` the section name used in checks (`"trainer"`, `"lessons"`...).
